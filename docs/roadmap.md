# Tunnelwright — направление развития

Текущее устройство — [architecture.md](architecture.md). Здесь — принятые решения, целевая
архитектура и порядок работ. Любое изменение кода сверяется с этим документом.

## Принятые решения (2026-10-30)

| # | Решение | Следствие для кода |
|---|---|---|
| 1 | **Коммерческий VPN-сервис**, только свой. Репозиторий закрывается, сторонних установок нет | Обратная совместимость нужна только с нашими серверами; публичный `install.sh` и импорт amnezia-wg — до переезда своих серверов |
| 2 | **Уходим от wg-easy до клиентского API.** Агент ноды сам управляет `amneziawg-go` / `awg` | Ключи и пиры — в панели; один ключ на устройство для всех нод; старые конфиги продолжают работать |
| 3 | **Доступ клиентов:** вручную админом, клиентский Telegram-бот, веб-кабинет | Одна сервисная логика для всех каналов: аккаунт, тариф, оплата, устройства |
| 4 | **Оплата:** ЮKassa / СБП, Telegram Stars, криптовалюта (CryptoBot) | Биллинг с подключаемыми провайдерами, идемпотентные webhook-и |
| 5 | **Свои приложения — позже**, Android и Windows: своя авторизация и продление в приложении. Пока клиенты пользуются сторонними AWG-клиентами по профилям | Всё новое проектируется под будущий `/api/client/v1`; профили `.conf` остаются рабочим путём |
| 6 | **SQLite, один экземпляр panel-api** | SQL без особенностей SQLite там, где это несложно, — чтобы переход на Postgres остался возможным |

## Целевая архитектура

```
домен админки:
  админ (браузер) ─────► /api/*            админка (текущий API, cookie-сессия, 2FA)
публичный домен:
  кабинет (браузер) ───► /api/client/v1    вход, тариф, оплата, устройства, конфиги
  приложения (позже) ──► /api/client/v1    тот же API, токен устройства
  платёжные системы ───► /api/billing/<провайдер>/webhook
внутри panel-api:
  клиентский бот ──────► сервисные модули напрямую, без HTTP

panel-api ──HTTPS + токен + закреплённый сертификат──► node-agent v2 ──► amneziawg-go (awg)
```

### Два API в одном panel-api

Админский и клиентский API — разные роутеры одного процесса над общими сервисными модулями,
не два сервиса.

| | Админский `/api/*` | Клиентский `/api/client/v1` |
|---|---|---|
| Потребитель | только админка, выкатывается вместе с бэкендом | веб-кабинет, позже приложения (живут годами на старых версиях) |
| Совместимость | меняется свободно | внутри `v1` — только совместимые изменения |
| Вход | `security.py`: пароль, 2FA, cookie-сессия админа | `client_auth.py`: Telegram, код, токен устройства; свои сессии |
| Видимость | всё | только свои данные: тариф, устройства, платежи |
| Защита | можно ограничить по IP/домену | публичный: лимиты частоты, защита от перебора |

- **Веб-кабинет работает только через `/api/client/v1`** — клиентский API проверяется на живых
  клиентах задолго до приложений. Текущая страница пользователя `/u/<токен>` остаётся как
  вход по ссылке и постепенно становится частью кабинета.
- **Сессии админов и клиентов не пересекаются:** разные таблицы, cookie и проверки.
  Клиентский токен никогда не открывает админский API, и наоборот.
- **Разделение по доменам.** Сейчас на «Адресе ссылок» закрыт весь `/api/*`, кроме `/api/host-check`
  (`user_host_only_pages` в `panel/app/main.py`). Там же открываются `/api/client/*` и
  `/api/billing/*`, админский `/api/*` остаётся закрытым. Админка — на своём домене, кабинет,
  клиентский API и webhook-и — на публичном.

### Слои panel-api

- **Роутеры тонкие** (`app/routers/*`): разбор запроса, права, ответ.
- **Сервисы** (`app/*.py`): вся бизнес-логика. Админка, кабинет, клиентский бот, webhook-и и
  будущий `/api/client/v1` вызывают одни и те же функции — правило «что можно сделать» живёт в одном месте.
- **Фоновые задачи** (`app/tasks.py`): синхронизация нод, трафик, сроки, квоты, бэкапы, напоминания об оплате.

### Модель данных (цель)

Есть сейчас: `users` (человек: срок, квота, группа, ссылка) → `clients` (устройство: один IP на всех
нодах) → `profiles` (устройство на ноде).

Добавится:

| Таблица | Назначение |
|---|---|
| `user_identities` | способы входа клиента: `telegram` (id), `email`; один пользователь — несколько способов |
| `user_sessions` | сессии кабинета и токены приложений (`client_auth.py`), отдельно от `sessions` админов; отзыв по устройству |
| `clients.public_key`, `clients.key_mode` | `device` — один ключ на все ноды (новые устройства); `per_node` — свой ключ в каждом профиле (перенесённые из wg-easy) |
| `clients.private_key_enc` | приватный ключ, только если его создала панель (QR/файл для сторонних клиентов); шифруется ключом панели. Ключи, созданные приложением, панель не видит никогда |
| `plans` | тариф: срок, число устройств, квота, лимит скорости, цены по валютам, видимость |
| `payments` | платёж: провайдер, внешний id (`UNIQUE(provider, external_id)`), пользователь, тариф, сумма в минимальных единицах, валюта, статус, время |
| `nodes.location`, `nodes.public_host`, `nodes.for_sale` | страна/город для выбора клиентом, публичный адрес, участвует ли нода в продаже |
| `node_interfaces` | интерфейсы ноды: порт, подсеть, параметры AmneziaWG, публичный ключ сервера |

Срок доступа остаётся `users.expires_at`: оплата продлевает его от `max(сейчас, expires_at)`.

### node-agent v2 (без wg-easy)

- Образ агента содержит `amneziawg-go` и `amneziawg-tools`; контейнер — с `NET_ADMIN` и `/dev/net/tun`.
- **Желаемое состояние:** панель передаёт полный список пиров интерфейса (публичный ключ, IP, лимит);
  агент применяет его `awg syncconf` и хранит у себя для запуска без панели.
- Приватный ключ сервера не покидает ноду; панель знает только публичный.
- Агент сам ставит NAT/forwarding, правила блокировки торрентов и `tc`-лимиты (последние два уже свои).
- Статистика — `awg show dump`: трафик и последний handshake по пирам.
- **Миграция:** агент читает `wg-easy.db`, переносит ключи сервера и пиров — конфиги клиентов не меняются.
  Перенесённые устройства получают `key_mode = per_node`.
- На время перехода у агента две реализации за одним интерфейсом: `wgeasy` и `awg`.

### Клиентский API `/api/client/v1` (под будущие приложения)

- Версия в пути. Внутри `v1` — только совместимые изменения: новые поля и методы, без удаления и
  смены смысла. Старые приложения живут годами.
- Вход: Telegram, код на email, код привязки из кабинета/бота. Ответ — токен устройства (отзывается).
- Устройство регистрируется со **своим публичным ключом**; панель выдаёт IP и создаёт пиры на всех нодах.
- `GET servers` — ноды и интерфейсы: адрес, порт, публичный ключ сервера, параметры AmneziaWG.
  Переключение ноды в приложении — смена адреса, ключ тот же.
- Тарифы, создание платежа, статус подписки — те же сервисы, что у кабинета и бота.
- Контракт описывается OpenAPI и проверяется тестами.

### Биллинг

- Провайдер — модуль с общим интерфейсом: создать платёж, проверить webhook, получить статус.
  Первые: ЮKassa (карты, СБП, чеки 54-ФЗ), Telegram Stars, CryptoBot.
- Статус оплаты берётся только из webhook-а или запроса к провайдеру, никогда со слов клиента.
- Webhook идемпотентен: повтор того же платежа ничего не меняет.
- Деньги — целые числа в минимальных единицах валюты (копейки, звёзды, центы).
- После оплаты: продление срока, применение лимитов тарифа, включение пользователя, уведомление.

## Порядок работ

1. **Основа.** `CLAUDE.md`, этот документ; ключ шифрования панели для секретов; разбить
   `web/src/App.jsx` на страницы перед работой над кабинетом.
2. **node-agent v2 без wg-easy.** Интерфейс туннеля в агенте → реализация `awg` → тесты на тестовой
   ноде (стек `dev`) → новые ноды без wg-easy → миграция существующих с сохранением ключей → удалить wg-easy.
3. **Модель устройств под приложения.** `key_mode`, один ключ на все ноды, интерфейсы нод, локации.
4. **Аккаунты клиентов и `/api/client/v1`.** `client_auth.py`, способы входа, сессии; открыть
   `/api/client/*` на публичном домене; веб-кабинет поверх клиентского API на месте страницы пользователя.
5. **Биллинг.** Тарифы, платежи, провайдеры, продление, напоминания до окончания срока.
6. **Клиентский Telegram-бот.** Отдельный токен; регистрация, оплата, конфиги, продление.
7. **Эксплуатация коммерческого сервиса.** Роли администраторов, мониторинг, ограничение частоты
   запросов публичных API, оферта и политика конфиденциальности.
8. **Позже:** приложения Android и Windows на `/api/client/v1` (отдельные репозитории).

## Открытые вопросы

- Юрлицо для ЮKassa (ИП / самозанятость) и чеки.
- Тарифная сетка: сроки, число устройств, пробный период, промокоды, рефералы.
- Домены: кабинет, API, страницы пользователей.
- Закрытие репозитория: `install.sh` берёт релизы из публичного GitHub, а ноды — образы из GHCR;
  после закрытия нужен доступ по токену или своя раздача релизов и образов.
